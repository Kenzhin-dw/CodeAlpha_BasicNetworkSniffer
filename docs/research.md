# Technical Research

## Requirements Analysis

The project needs live capture on Windows 10/11, extraction of IPv4/IPv6 and transport-layer metadata, basic protocol classification, statistics, and a responsive Streamlit dashboard. The capture API therefore needs to expose packet layers directly to Python, support explicit interface selection, and run safely in a background worker. It should not collect raw application payload by default: payload presence and length are sufficient for the internship requirement and reduce privacy risk.

The target is a teaching and demonstration tool for traffic generated by the user's own computer, not a high-throughput forensic appliance. Reliability, understandable code, and a short Windows setup are more important than exhaustive protocol decoding.

## Selected Technology

Use **Python 3 + Scapy + Pandas + Streamlit**, with **Npcap** as the Windows capture driver.

Scapy is selected because it combines capture and layer-aware parsing in one Python library. Unlike raw `socket`, it avoids implementing protocol structures from scratch; unlike PyShark, it does not require coordinating a separate TShark process. This is the simplest stack that can cleanly expose source and destination addresses, protocols, ports, flags, lengths, summaries, and safe payload metadata.

Scapy's `AsyncSniffer` has `start()`, `stop()`, and `running` controls, making it suitable for a single managed capture worker. The application should still own the lifecycle and shared data explicitly so Streamlit reruns do not create duplicate sniffers. See the official [`AsyncSniffer` API](https://scapy.readthedocs.io/en/stable/api/scapy.sendrecv.html#scapy.sendrecv.AsyncSniffer).

PyShark remains a reasonable future option if the project later needs Wireshark's much broader dissector set. It is not selected for this deadline-oriented build because its official project description confirms that it delegates parsing to TShark rather than parsing packets itself ([PyShark README](https://github.com/KimiNewt/pyshark)).

## Windows Packet Capture Requirements

### Npcap

Npcap is required for Scapy's supported Windows capture path. It installs the packet-capture driver and libpcap-compatible API that Scapy uses to enumerate interfaces and receive packets; without it, live Windows capture will not work through this architecture. Scapy explicitly directs Windows users to install Npcap and describes old WinPcap as unsupported nowadays ([Scapy installation guide](https://scapy.readthedocs.io/en/stable/installation.html)). Wireshark independently documents Npcap as required for Windows live capture ([Wireshark Windows installation guide](https://www.wireshark.org/docs/wsug_html_chunked/ChBuildInstallWinInstall.html)).

### WinPcap compatibility mode

WinPcap compatibility mode is **not required for this project**. Scapy's installation guide advises turning that option off. Enable it only when a separate legacy application specifically requires WinPcap-compatible DLL placement. Avoid installing legacy WinPcap alongside Npcap: Scapy documents DLL conflicts when both are present ([Scapy troubleshooting](https://scapy.readthedocs.io/en/latest/troubleshooting.html)).

### Administrator requirements

- Installing the Npcap driver requires Windows elevation.
- For the simplest and most predictable demonstration, start the terminal that launches Streamlit with **Run as administrator**.
- Capture is not unconditionally administrator-only after installation. Npcap can be installed with an `admin_only` option; when selected, its device ACL permits only SYSTEM and built-in Administrators and uses a UAC helper. Without that restriction, local users may be allowed to open the loaded driver. This behavior is documented in the [Npcap Users' Guide](https://npcap.com/guide/npcap-users-guide.html) and [Wireshark capture-privileges guidance](https://wiki.wireshark.org/capturesetup/captureprivileges).

### Common Windows issues

- **No interfaces or no packets:** Npcap may be missing, its `npcap` service may not be running, the process may lack access, or the wrong adapter may be selected. Generate traffic, compare adapter descriptions/addresses, and test active adapters one at a time.
- **Npcap/WinPcap conflict:** remove legacy WinPcap rather than keeping both implementations and competing `wpcap.dll`/`Packet.dll` files. Follow [Scapy's conflict procedure](https://scapy.readthedocs.io/en/latest/troubleshooting.html).
- **Promiscuous-mode warning:** some adapters or drivers cannot enable it. Scapy documents `conf.sniff_promisc = False` as the workaround; this is adequate for capturing traffic addressed to or generated by the local machine ([Scapy troubleshooting](https://scapy.readthedocs.io/en/latest/troubleshooting.html)).
- **Loopback traffic absent:** modern Npcap exposes loopback as `\Device\NPF_Loopback`; legacy loopback installation support is not needed for Wireshark and modern Npcap. The dashboard must select that loopback interface to observe `localhost` traffic rather than the Wi-Fi/Ethernet adapter ([Npcap development guide](https://npcap.com/guide/npcap-devguide.html)).
- **Odd checksums or oversized packets:** Windows NIC offload features can make locally captured packets appear to have incorrect checksums or unusually large segments. This is normally a capture-view artifact, not corrupted network traffic ([Npcap Users' Guide](https://npcap.com/guide/npcap-users-guide.html)).
- **Only TCP handshakes/teardown appear:** Npcap documents old TCP Chimney offload as a possible cause. Disable that deprecated adapter feature if present ([Npcap Users' Guide](https://npcap.com/guide/npcap-users-guide.html)).
- **Wi-Fi monitor-mode limitations:** raw 802.11 monitor mode depends on adapter/driver support and is not needed for this project. Normal capture of the computer's own traffic should use the standard Wi-Fi interface.

## Proposed Architecture

```text
Windows network interface
        |
        v
Npcap + Scapy AsyncSniffer (one managed background capture worker)
        |
        v
Packet parser (IP/IPv6, TCP/UDP/ICMP, DNS, safe payload metadata)
        |
        v
Bounded, lock-protected in-memory packet store
        |                         |
        v                         v
Live packet table          Statistics functions
        |                         |
        +------------+------------+
                     v
              Streamlit dashboard
                     |
                     v
            Filtered CSV metadata export
```

Capture, parsing, statistics, UI, and export should remain separate modules. The sniffer callback should do minimal work, append parsed records to a bounded store under a lock, and never call Streamlit APIs. Streamlit should read a snapshot of that store on each refresh. A single controller instance should own `start`, `stop`, and shutdown behavior so reruns cannot create duplicate capture threads.

## Limitations

- A capture normally sees traffic processed by the selected local interface, not arbitrary traffic between unrelated devices on a switched network. The tool is restricted to systems and networks the user owns or is authorized to inspect.
- HTTPS/TLS application content is encrypted. The sniffer can show connection metadata and recognize likely TLS traffic, but it will not decrypt it.
- Protocol classification is best-effort. Ports are useful hints, while nonstandard ports, tunneling, encryption, and ambiguous payloads can prevent exact identification.
- Promiscuous mode and Wi-Fi monitor mode are different. Monitor mode is hardware/driver-dependent and outside this project's scope.
- Python and Streamlit are suitable for an internship demonstration, not lossless capture on saturated high-speed links. A bounded buffer may intentionally discard older display records to keep the UI responsive.
- Interface names and permissions vary by machine. Live capture and loopback capture therefore require manual verification on the target Windows computer with its installed Npcap driver.
- NIC offloading can produce checksum and segment-size artifacts in captures. The dashboard should present metadata as observed and avoid claiming forensic fidelity.
